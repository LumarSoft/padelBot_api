## Architecture

**Framework:** NestJS v11 with TypeScript (target ES2022, `CommonJS` module / `node` resolution).

**Database:** MySQL via Prisma v7 (using `@prisma/adapter-mariadb`). The Prisma client is generated to `generated/prisma` (gitignored — run `npx prisma generate` after cloning). Always import from `'generated/prisma/client'` (resolved via `baseUrl: "./"` in tsconfig).

**Prisma v7 config:** Configuration lives in `prisma.config.ts`, not in `schema.prisma`. The datasource block in `schema.prisma` has no `url` — the connection string is resolved at runtime from `env('DATABASE_URL')` in `prisma.config.ts`. The generator uses the new `prisma-client` provider (not `prisma-client-js`), which is why output goes to `generated/prisma` and `PrismaService` is constructed with an explicit `PrismaMariaDb` adapter rather than a bare `PrismaClient`.

**Auth stack:** JWT via `@nestjs/jwt` + `@nestjs/passport` + `passport-jwt`, passwords hashed with `bcrypt`. The JWT payload carries `clubId`, `role`, `name`, `email` (`src/auth/types/jwt-payload.ts`). Protect routes with `@UseGuards(JwtAuthGuard)` and read the caller with the `@CurrentUser()` decorator. `OWNER` vs `STAFF` is enforced per-controller (e.g. only OWNER can change payment settings).

**Env vars:** `DATABASE_URL` (Prisma, loaded via `dotenv/config` in `main.ts`), `JWT_SECRET`, `ENCRYPTION_KEY` (AES key used by `CryptoService` to encrypt MercadoPago tokens at rest), Meta WhatsApp credentials, and MercadoPago OAuth (`MP_*`) credentials. Server port defaults to `3000` (`process.env.PORT`). Copy `.env.example` → `.env` and fill in the values.

**DTO validation:** `ValidationPipe` is configured globally in `main.ts` with `whitelist`, `forbidNonWhitelisted`, and `transform`. Use `class-validator` decorators on all DTOs.

**Module structure:** Standard NestJS feature modules — each domain gets its own directory under `src/` with `module`, `controller`, `service`, and `dto/` files. Register new modules in `AppModule`.

## Product & domain

This is **GTP**, a multi-tenant SaaS for padel clubs in Rosario, Argentina (see `../docs/BITACORA.md` for the product story). A WhatsApp bot attends players, books courts and reconciles the deposit ("seña") transfer automatically; owners manage everything from the Next.js panel (`../front`). The data model and tenant boundaries live in `prisma/schema.prisma` — **read it first**; it is the source of truth.

**Multi-tenant of record:** `Club` is the tenant. Every relevant row (`Court`, `Slot`, `Booking`, `RecurringBooking`, `WhatsAppLine`, `ConversationSession`, `User`) carries a `clubId` and is isolated per club. **Never** write a query that can cross tenants — always scope by the caller's `clubId` from the JWT.

**Feature modules (all built and wired in `AppModule`):**

- `auth` — JWT login, guard, `@CurrentUser()` decorator, `OWNER`/`STAFF` roles.
- `onboarding` — managed club signup (`POST /onboarding/request` captures the lead; ops-only `POST /onboarding/register` provisions an **empty** Club + OWNER on a trial — no demo data), plus the **guided account setup** behind the panel's `/setup` wizard: `GET /onboarding/status` aggregates the state of the seven setup steps, `PATCH /onboarding/progress` stores the resume position on `Club.setupProgress`, `POST /onboarding/complete` sets `Club.setupCompletedAt`. Each step's `done` is **derived from the club's real data** (`OnboardingService.getStatus`), never trusted from the stored progress blob, so a club configured by hand reads as done. Every step is skippable; `ready` gates only on the three the bot can't run without (courts, payment config, WhatsApp line).
- `clubs` — per-club transfer config (alias/holder) and **MercadoPago Connect OAuth** (each club connects its own MP account; tokens stored encrypted via `CryptoService`, refreshed by the poller before expiry).
- `courts` — physical courts (`name`, `priceCents`, `openTime`/`closeTime`, `courtType` INDOOR/OUTDOOR).
- `slots` — bookable time bands (`turnos`); supports bulk-blocking. Unique `(courtId, startsAt)` prevents concurrent admin+bot from duplicating a slot.
- `availability` — derives open bands from a court's schedule. **Slot duration is the hardcoded constant `SLOT_DURATION_MINUTES = 90` in `availability/lib/schedule.ts` — it is NOT yet a per-court field.** Making it configurable (with the 90-min padel default) is a roadmap item.
- `bookings` — reservations with a `BookingStatus` state machine (`PENDING_PAYMENT` → `CONFIRMED` / `CANCELLED`), reschedule, cancel.
- `recurring-bookings` — weekly fixed reservations (`turnos fijos`) auto-applied to matching slots.
- `whatsapp` — Meta WhatsApp Business webhook (verify + receive), with dedup of Meta retries via `ProcessedWebhookMessage`.
- `whatsapp-lines` — maps a Meta `phoneNumberId` to a club so the bot resolves the tenant of an incoming message.
- `bot` — the conversational state machine + `ConversationSession` persistence; AI/HUMAN takeover mode.
- `llm` — LLM with tool-calling (`llm/tools.ts`, `llm/system.prompt.ts`) that interprets messages and executes booking actions. Every OpenAI failure degrades quietly for the player ("no entendí", audio or receipt not read) and never throws. OpenAI is prepaid, so the account-level ones alert ops via `notifyOps`, once per kind per hour (in-memory, like Meta's 131042): 429 `insufficient_quota` (no credit: top up in platform.openai.com Billing or turn on auto-recharge) and 401 (invalid or revoked `OPENAI_API_KEY`). A plain rate limit or a 5xx stays a log line.
- `conversations` — persistent per-message log (`ConversationMessage`), admin manual replies, AI/HUMAN mode switch.
- `payments` — transfer reconciliation against MercadoPago, including the **centavos trick**: when two pending bookings collide in the same whole-peso bucket, each gets a distinct `transferAmountCents` so one incoming transfer maps to exactly one pending booking.
- `mercadopago` — MercadoPago API client + OAuth token exchange/refresh.
- `events` — Server-Sent Events (`booking-events.service.ts`) so the panel reflects bot bookings in real time.
- `stats` — `GET /stats/overview` aggregates per-club dashboard metrics (today's turnos, active reservations, active chats, pending payments, deposits collected, bot-vs-panel bookings, and a 14-day series).
- `help` — in-context help for the panel, built for desk staff first (no courses: receptionists rotate every 1–3 months and don't read) and extended to the owner. `GET /help/first-day` is the per-user **"Tu primer día" checklist**, derived from real data like `OnboardingService.getStatus`: `booking` from `Booking.bookedByUserId`, the rest from `UserFirstAction` (one row per user and `DeskAction`), written by the global `DeskActionInterceptor` after any endpoint marked `@RecordsDeskAction(...)` succeeds — mark a new desk action there, never in the service. Also the club's **house rules** (`Club.houseRules`, same shape as `botFaq`, owner-edited, never reaches the bot) and `HelpSearchMiss` (help searches with no result, per club; read by the ops console), plus `User.newsSeenId`: the newest panel "Novedades" entry each user has seen (`GET`/`POST /help/news/seen`), stored server-side so the dot on the owner's "?" holds across devices. The questions, "Mostrame" guides and news entries themselves live in the panel (`front/src/features/help`).
- `ops` — the **Lumarsoft ops console** (`/ops` in the panel), and the ONE module that reads across tenants on purpose: the lead pipeline from the `/register` form (+ provisioning a club straight from a lead), the tenants table, business/bot metrics (MRR, activation, bot-vs-panel, OpenAI cost per club) and cross-club system health. Two things keep the tenant boundary honest: the identity is a `PlatformAdmin` (no `clubId` — a club `User` can never be one), and its JWT is signed with **`OPS_JWT_SECRET`, not `JWT_SECRET`**, so a club token doesn't verify against `OpsAuthGuard` and vice versa. The console is **opt-in**: with `OPS_JWT_SECRET` unset it disables itself (login 503s, no token validates) and the club API is untouched — never crash the tenants' product over an internal tool. Bootstrap an operator with `npm run ops:admin`.
- `plans` — the three commercial plans the landing sells (`saque` / `bandeja` / `smash` on `Club.plan`; catalog in `plans/lib/plans.ts`, kept in step with `front/src/features/landing/lib/plans.ts`). Global module (like `PricingModule`) because unrelated modules ask it. Same rule as `clubs/lib/subscription.ts`: **a plan never takes anything away abruptly**. Courts and active users (owner included) are soft limits — `PlansService.assertCanAddCourt` / `assertCanAddUser` refuse only one more. Modules (fijo confirmation, kiosk stock, waitlist offer, split payment, scheduled price rises) are refused only when being turned ON (`assertFeature`); what a club already runs keeps working, and clubs created before the plans have `Club.grandfatheredFeatures` (every module, until ops clears it). Split payment never blocks the desk: without it a payment must cover the whole bill. Credits ("créditos de IA" to the club) = one per WhatsApp message the BOT sends (`CreditsService`, fed by every send Graph accepts in `WhatsAppService`; `WhatsAppMessageDaily` per number and day, split bot / staff / utility template so it also gives our Meta cost). AI steps stay in `LlmUsageDaily` as cost only. A credit stands for one bot message plus the AI an average message takes; there is nothing to buy. `AiCreditAlertsService` (every 5 min) warns ops (`notifyOps`, with the plan to offer) and the club (push: owners, everyone at 100%) at 80/90/95/100% once per month each. **At 100% the bot is PAUSED** (`CreditsService.botPaused`, `creditsPaused` in `plans/lib/ai-credits.ts`; never the sales demo or an unknown plan): `BotService` keeps the player's message for Conversaciones, tells each conversation once that the club answers by hand and pushes the staff; reminders, fijo confirmations and waitlist offers skip the club; payment messages still go out. It resumes when the club is on a bigger plan or the month turns. Ops sees it as the `botPaused` club state and a `BOT_PAUSED_NO_CREDITS` health issue. A send Meta refuses for payment (131042) alerts ops. An unknown plan key restricts nothing. `GET /clubs/me/plan` feeds the panel.
- `billing` — `GET /billing` feeds the owner's Facturación page: plan, subscription and the month's credits against the plan. Credit packs were removed on 2026-10-15 (never sold); clubs can't buy credits, only change plan.
- `ops` follow-up and growth tools: each club's **ficha** (`GET /ops/clubs/:id`, `OpsClubDetailService`: its row, `Club.opsNotes`, the lead it came from, 6 months of credits, bot/panel bookings and margin); the lead **follow-up** (`ClubSignupRequest.followUpAt` → `GET /ops/leads?due=today`, `lostReason` when marking LOST, `utm*` from the signup); the **signup funnel** (`POST /onboarding/funnel`, public and anonymous: one count per `/register` screen per page load in `SignupFunnelDaily` → `GET /ops/signup-funnel`); the **monthly business** (`OpsMonthStatesService` records each club's subscription per month in `ClubMonthState` — daily, on boot and after console changes — for MRR, new paying clubs and churn in `GET /ops/metrics/business`, which leaves the sales demo out); and the **Monday summary** (`OpsWeeklySummaryService`, 9:00 club-local, to `OPS_ALERT_WEBHOOK_URL`; `GET /ops/weekly-summary` previews it).
- `ops` profitability (`GET /ops/profitability`) converts Meta's and OpenAI's USD costs with `ExchangeRateService`: the dollar (`USD_ARS_QUOTE`, `oficial` by default: Lumarsoft pays Meta and OpenAI in dollars) is fetched daily from dolarapi.com into `ExchangeRate`, a month uses its last stored quote, and ops is alerted if the fetch keeps failing — no rate to update by hand.
- `products` / `stock` — the kiosk catalog and its **opt-in stock** (`Product.stockQuantity` null = not tracked). `StockService` keeps the "entra / sale / queda" ledger (`StockMovement`: PURCHASE / SALE / ADJUSTMENT, signed quantity + `stockAfter`); every stock change writes its ledger line in the same transaction, and `BookingsService.setBookingProducts` moves stock by the **net change** of the bill inside the transaction that rewrites the consumos. Endpoints (open to STAFF): deliveries, physical counts (difference stored as ADJUSTMENT and returned), the "para comprar" list, per-product history and **counter sales** (`CounterSale`, a sale without a turno — counted by `/stats/revenue`). A sale is never blocked for lack of stock (it can go negative). When a product drops to its minimum the OWNER gets one push (`NotificationsService.notifyOwners`), guarded by `Product.lowStockNotifiedAt` until it's restocked. **Barcodes** for the panel's point of sale: `Product.barcode` (optional, trimmed by `products/lib/barcode.ts`, unique per club via `@@unique([clubId, barcode])` — `ProductsService` names the product that already has it in the 409) and `GET /products/by-barcode?code=` to resolve a scan. The POS adds no write endpoint of its own: «Cobrar» posts the scanned ticket as one counter sale, «Cargar stock» the scanned delivery as one purchase. Creating products is open to STAFF too (the counter creates one when it scans an unknown code).
- `booking-reminders` — cron (`EVERY_5_MINUTES`) that WhatsApps a player ~1h before their confirmed slot via a Meta message template (required outside the 24h session window). Needs `WHATSAPP_REMINDER_TEMPLATE_NAME`/`_LANG` approved per club's number to actually deliver; `Booking.reminderSentAt` guards against duplicate sends and is reset on reschedule.
- `fixed-confirmations` — automatic attendance check for the fijos (`docs/FIXED_CONFIRMATIONS.md`). `Club.fixedConfirmationLeadHours` before each fixed booking (default 24, opt-in via `fixedConfirmationEnabled`) a cron sends a Meta template with quick replies "Sí, voy" / "No puedo" whose payloads carry the booking id (`WHATSAPP_FIXED_CONFIRMATION_TEMPLATE_NAME`/`_LANG`). The webhook routes `message.type === 'button'` taps here: it checks the booking belongs to the line's club AND the number that tapped, is idempotent, and "No puedo" cancels ONLY that date (`BookingsService.cancel` with `attendanceDeclined` → waitlist) while the `RecurringBooking` keeps going. No answer never cancels: the staff gets a push ~2h before. A fijo that was asked (`attendanceAskedAt`) skips the 1h reminder — one template per turno.
- `competitions` — **torneos and peñas** (`Competition.kind` TOURNAMENT / PENA), run by the desk from the panel or the app. The bot only takes sign-up requests: menu option 3 / "torneo"-like words / the LLM's `show_competitions` tool list the OPEN events with a session ahead (`CompetitionSignupsService.openForPlayers`, picker in `bot/lib/competitions.ts`, state `COMPETITION_PICK`); picking one stores a `CompetitionSignupRequest`, pushes the club, emits SSE `competition.signup` and hands the chat to a person (`requestAdvisor`: HUMAN + `needsAdvisor`). The desk registers the pair; the panel's header inbox lists the requests. An event holds courts during one or more sessions (club-local `dateKey` + "HH:MM" window): every band of the grid overlapping a session becomes a BLOCKED slot tagged `Slot.competitionId` (`syncBlocks`; a booked turno in the way refuses the whole change with a 409 listing them, cancelling/deleting frees them, `bulk-unblock` never touches them). Pairs are registered by staff (two `CompetitionPlayer`s, phone optional and linked to `Player` via `upsertForBooking`), fee **per player** with paid/method per player. Categories are `ROUND_ROBIN` (a peña is one, "General", packed in waves over the courts), `GROUPS_KNOCKOUT` (zonas, then a bracket seeded from the tables) or `KNOCKOUT`; results are sets from pair A's side (`ONE_SET` americano/peña or `BEST_OF_THREE` completo) and a knockout winner moves on by itself. The draw, scoring and tables are pure helpers in `competitions/lib/` with specs. Every write emits SSE `competition.changed`. Open to every plan.
- `improvements` — **"Mejoras"** in the panel and the staff app (OWNER and STAFF). `Improvement` is global (no `clubId`, like `PlatformAdmin`): what Lumarsoft shipped or plans (`PLANNED` / `IN_PROGRESS` / `RELEASED`), visible to clubs once `publishedAt` is set (`GET /improvements`). `ImprovementSuggestion` is tenant-scoped: a club's owner or staff proposes one (`POST /improvements/suggestions`, pinged to `notifyOps`) and sees only its own club's with our reply (`GET /improvements/suggestions`). We post and answer from the ops console (`OpsImprovementsService`: `/ops/improvements`, `/ops/improvement-suggestions`) or from the shell with `npm run improvement:post -- --title '…' --body '…'` (`--status`, `--draft`, `--suggestion <id>` to mark suggestions answered). Separate from the panel's "Novedades" (static, tied to on-screen guides).
- `demo` — the **sales demo club** ("Distrito Pádel", slug `distrito-padel`) we show to prospects. `sales-demo.seed.ts` builds two months of history + the coming weeks (bookings, fijos, players, kiosco, chats written with the bot's real copy); `DemoService` rebuilds it nightly at 05:00 and, 08:00–23:30, `sales-demo.live.ts` simulates a bot booking every 15–25 min and confirms its seña 16–24 min later, so the demo is always fresh. It only acts if that club exists (create it with `DEMO_PASSWORD=… npm run demo:seed`), only touches demo players (phones `5493410…`, a range that doesn't exist), and `DEMO_AUTOPILOT=false` turns it off. The nightly rebuild wipes that club's content (keeps users, WhatsApp line, MercadoPago and alias).

**Payment policy (seña / full / none):** what the bot asks the player to transfer is per-club config on `Club`: `depositMode` (`DEPOSIT` = a seña of `depositPercent`% of the court price, default 25%; `FULL` = the whole court price; `NONE` = nothing — the bot works as a booking book: name, day, time, and the booking is created **CONFIRMED** on the spot with no `transferAmountCents`, no `paymentExpiresAt` and no alias shown). `BookingsService.resolvePaymentPlan` computes the amount; **a seña that works out to $0 (a court with no price) books exactly like `NONE`**. With `NONE` the poller, the centavos trick, the expiry sweep, `requireDniMatch` and player credit never come into play (nothing is pending), the onboarding `pagos` step counts as done without MercadoPago or alias, and a player at the no-show threshold is handed to the club (push + "te responden por acá") instead of being asked the full price. The bot's wording adapts in `messages.ts` and the LLM prompt states the club's policy. The owner sets this in the panel's Pagos tab. (Per-player choice at booking time is a future extension — see ROADMAP.)
- `common/crypto` — AES encrypt/decrypt for secrets at rest. `common/filters` — global exception filter.

**What's NOT built yet (see `../docs/ROADMAP.md`):** self-service onboarding (alta of a club without manual DB work), SaaS billing of GTP itself, configurable slot duration per court, "tipo de complejo" and multi-venue (one brand with several addresses), and automated tests of the critical flows.
